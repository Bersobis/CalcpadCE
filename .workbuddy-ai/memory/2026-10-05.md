## Live editor — architecture options study (no code changed)

Report: `Calcpad.Web/frontend/LIVE-EDITOR-APPROACHES.md`.

Decisive facts established (verified against the installed libs / repo):
- MathLive 0.111 is LaTeX-pivoted: input is LaTeX only (docs), MathML is an OUTPUT format
  (`getValue('math-ml')`), and `mathlive/ssr` exposes `convertLatexToMathMl(latex)` — i.e.
  MathML is derived FROM LaTeX. No OMML support, no MathML input. So LaTeX cannot be
  removed while keeping MathLive; there is no free MathML-native WYSIWYG editor.
- `Calcpad.Core` is net10.0 and pulls SkiaSharp 3.119.1 + System.IO.Packaging, and via
  `Calcpad.OpenXml` also DocumentFormat.OpenXml 3.3.0 + HtmlAgilityPack. Browser-hostile
  code lives in Plotter/Plotter.cs, PathRoots.cs, ExpressionParser.DataExchange.cs,
  ExpressionParser.Portable.cs. => Blazor WASM is feasible but expensive.
- Backend `/convert` returns HTML only (no MathML mode); `/docx` already emits OMML
  (captureOpenXml). Other endpoints: /lint /highlight /definitions /symbol-at-position
  /prettify /snippets /pdf /cpdz/* /portable/*.
- The live editor duplicates the C# engine in TS (`math/calcpad.ts` ~920 lines parser +
  `math/latex.ts` ~950), and only edits lines whose TS round-trip is exact
  (`classifyLineEdit`).

Recommendation recorded: Phase 1 single source of truth = extend `/convert` with a MathML
output mode and let the client render from it (Monaco stays the authoring surface);
Phase 2 render regions as MathML; Phase 3 only if 2D entry is required, add MathLive with
LaTeX confined to one adapter. Blazor WASM / native C# deferred (they don't solve the
editing-widget problem and cost a second UI framework / WASM payload).

Note: the earlier "confine LaTeX + MathML/OMML out" refactor was NOT implemented — that
turn only read files and asked; the working tree still holds only the first audit's changes.

## Live editor — Nim/Rust feasibility study (no code changed)

Report: `Calcpad.Web/frontend/LIVE-EDITOR-NIM-RUST.md`.

Measured port target (excluding obj/bin): Core 43,422 / Highlighter 22,653 / backend 6,504 /
OpenXml 2,459 / Cli 1,310 / Api 669 = ~77,000 production LOC; Calcpad.Tests 54,831 LOC.
Rust is ALREADY a project dependency: `calcpad-desktop/src-tauri` = 1,604 lines Rust with
committed Cargo.toml/Cargo.lock. No Nim and no `.wasm` anywhere in the repo.
De-risking asset: ~249 `.cpd` + ~231 `.stub` golden files in Tests/Examples/cli-build are a
language-agnostic rendering oracle — a port can be validated without reading C#.

Conclusion recorded: both technically possible; Rust is the better of the two and neither
should replace the C# engine. Reasons: (1) the live editor's bottleneck is the MathLive
widget, which is JS-only and has no Rust/Nim equivalent, so neither language removes LaTeX
or delivers 2D entry; (2) performance is not a constraint (engine runs in ms, cost is DOM
rendering); (3) Nim's only wins (compile speed, binary size, syntax) are not binding, while
its WASM maturity and numeric/plotting/OOXML ecosystem are materially weaker.
The one place Rust genuinely earns its place: a narrow WASM parser/evaluator core, which
would kill both the TS/C# duplication and the server round-trip — a much more practical
variant of the earlier Blazor-WASM option.

## Live editor — problem framing reframed (no code changed)

Report: `Calcpad.Web/frontend/LIVE-EDITOR-PROBLEM-STATEMENT.md`.

Corrected the earlier claim "performance is not the bottleneck" — which read as a defence of
the current design. Reframed as: the editor IS slow and fragile, and the root cause is
**design duplication** (engine implemented twice: `math/calcpad.ts` + `math/latex.ts` on the
client vs `Calcpad.Core` on the server), NOT TypeScript being slow.

Slowness mechanisms (all visible in code): work done twice; `classifyLineEdit`→`checkLine`
runs a full parse/print/re-parse/to-LaTeX round-trip per line because the client cannot trust
its own parser; that runs inside the `regions` computed over the whole document; one MathLive
instance per equation region.
Fragility mechanisms: two parsers must agree by hand; disagreement surfaces as a line quietly
reclassified `lossy` (lost capability, not an error); two independent test suites can both
pass while disagreeing.
Ruled out: TypeScript throughput — the redundant work is algorithmic, so a faster language
would only produce a faster duplicate (ties back to the Nim/Rust conclusion).
Included a falsifiable confirmation plan (count round-trips, time the gate, count widgets,
test drift by changing a Core parsing rule only).
