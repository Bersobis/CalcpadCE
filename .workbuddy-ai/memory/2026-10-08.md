# 2026-10-08 — Fixed NETSDK1047 breaking the desktop sidecar publish

Branch: `Experimental-Live-Editor`. Reported failure was in the Tauri build's
sidecar step:

```
error NETSDK1047: Assets file '...\Calcpad.Web\backend\obj\project.assets.json'
doesn't have a target for 'net10.0/win-x64'.
[sync-bundled-server] FAILED: Command failed: dotnet publish ... -c Release -r win-x64 ...
At stage-sidecar.ps1:32 -> throw 'Sidecar publishing failed'
```

The NETSDK1047 suggestion (add `win-x64` to `RuntimeIdentifiers`) is a red herring.
The csproj already targets `net10.0` and nothing needs a standing RID list.

## Root cause

`obj/project.assets.json` holds **one** restore graph per project. Restoring
without a RID *replaces* it with a single `net10.0` target, dropping
`net10.0/win-x64`. A RID-less `dotnet build -c Release` — an IDE build, a manual
build, or a sibling project's build — therefore poisons the graph for the later
`-r win-x64` publish. Verified directly:

| step | `targets` in assets file |
|---|---|
| `dotnet build` (no RID) | `["net10.0"]` |
| `dotnet restore -r win-x64` | `["net10.0","net10.0/win-x64"]` |
| `dotnet build` (no RID) again | `["net10.0"]` ← replaces, does not stack |

`dotnet publish` only restores implicitly when it decides it needs to, and after
a RID-less build its "All projects are up-to-date for restore" check can pass on
the stale graph — hence the failure instead of a silent self-heal.

## Fix

`Calcpad.Web/frontend/vscode-calcpad/scripts/sync-bundled-server.mjs` — new
`restoreForRid(rid, configuration)`, called before publish whenever
`--skip-build` is absent. It always re-restores the RID graph first, so publish
is self-sufficient regardless of what ran before it. No-op-cheap when the graph
already matches. Both `stage-sidecar.ps1` and `stage-sidecar.sh` go through this
one script, so one change covers every platform.

```js
run(`dotnet restore -r ${rid} -p:Configuration=${configuration} "${CSPROJ}"`, BACKEND_DIR);
```

Note the flag form: `dotnet restore` forwards only `-r` to the implicit Restore
target. `-c` leaks through to MSBuild, which wants `-p:Configuration=` — passing
`-c` fails with **MSB1001 "Unknown switch"**. Both variants were tried and failed
before landing on the property form.

## Verification

Reproduced the failure ordering exactly and drove it to green end to end:

1. Poisoned the graph with a RID-less Release build → `["net10.0"]`.
2. Deleted the publish output so a real rebuild had to happen.
3. Ran the real entry point, `powershell -NoProfile -ExecutionPolicy Bypass -File
   stage-sidecar.ps1`, exactly as `desktop.mjs` does:
   restore-for-RID → publish → `OK — bundle size 30.2 MB` → staged to
   `src-tauri/binaries` → mirrored into `target/debug` and `target/release`. **exit 0.**
4. Booted the staged `Calcpad.Server.exe`: `GET /api/calcpad/health` → `200
   {"status":"ok"}`.

Also confirmed a plain `dotnet build Calcpad.Server.csproj -c Release` (the
RID-less form, i.e. what originally poisoned it) still succeeds — the fix
prevents the failure without constraining how you build normally.

## Gotchas worth remembering

- Node's `execSync` with `stdio: 'inherit'` writes straight to the parent's
  console, so a `node ... .mjs` run **swallows its own banners** in some
  non-interactive hosts — you see only the child `dotnet` output. Redirect to a
  file if you need the full log.
- The sandbox blocks `powershell` invoked from Bash and blocks `Start-Process`
  for shells/interpreters. Use the PowerShell tool, and for a one-shot run
  `powershell.exe -NoProfile -ExecutionPolicy Bypass -File <script>` works.
- A detached `&` from Git Bash does not survive the shell teardown. To keep a
  server alive across commands: `cmd //c "start /b Calcpad.Server.exe --urls ..."`.

# 2026-10-08 (later) — MathLive review + LaTeX-free editor design brief

Wrote **`docs/mathml-equation-editor-design.md`** (605 lines), registered in `mkdocs.yml`
under "New Apps and Features (beta)" next to the WYSIWYG brief. Deliverable was a design
brief + phased plan; user chose **client-only bridge** (no backend change) and scope =
widget + integration constraints.

## Framing correction (the important bit)

**MathLive is already gone from this repo** — `grep -i mathlive` over the frontend returns
nothing; branch `Experimental-Live-Editor` replaced it with the MathML live display. So the
brief is about *hardening an existing component*, not building one. Two claims about MathLive
that circulate and are **wrong**, both corrected in the doc:

- There is no `@cortexjs/core` package — the scope is `@cortex-js`, and `@cortex-js/compute-engine`
  is now optional. Current MathLive has **zero runtime deps**.
- The fonts are **KaTeX** (`KaTeX_Main`…), not Latin Modern Math. Metrics are a ~92 KB
  **baked table** generated offline from TeX TFM (`tftopl cmsy10/cmsy7/cmsy5`), not read from
  the font's MATH table at runtime.
- MathLive **emits** MathML but never *renders* from it — rendering is its own box engine.

## The design thesis

Calcpad's **input language and storage language are the same** (flat operator language; the 2D
structures are *derived from operators*: `/ ^ _`). So the LaTeX⇄model layer is **deleted, not
replaced**, and the box-layout engine is replaced by **native browser MathML typesetting**.
Deletes: layout subsystem, metrics payload, font payload, per-instance editor cost.

## Highest risk (found by pressure-testing)

**Native MathML is not guaranteed on the Linux/macOS Tauri hosts.** `tauri.conf.json` sets
`macOS.minimumSystemVersion: "11.0"` → macOS 11 = Safari 14, which predates MathML Core
(Safari 16.4). WebKitGTK needs 2.40+. Nothing in the repo probes this. Phase 0 is therefore a
**measured DOM probe** + fallback + one bundled math woff2, before anything else.

## Concrete defects catalogued (all verified with file:line)

- `equalNodes` (`ast.ts:154-162`) **ignores attributes** — latent gate blind spot.
- `partialTypesetMarkup(editable)` **re-parses per keystroke** (`CalcpadLiveDisplay.vue:526`)
  while the editor already holds the tree.
- `anchorsOf` re-walked several times per keystroke (`anchorIndex` ×2 + `lastAnchor` +
  `hasEmptySlot`).
- `lineEditorModel` / `plainMarkup` exported but **unused** by the app.
- Typing `>` then `=` makes two `mo` tokens that re-parse as `≥` → **the gate can decline a
  line the user just edited** (`calcpad.ts:73-85` normalises `!= <= >= ==`).
- `PRINTABLE` (`CalcpadMathMlEditor.vue:254`) includes `∠`/`,` but omits `←`/`÷`; the parser's
  `OPERATOR_CHARS` (`calcpad.ts:38`) is the mirror image — the two sets must come from one source.
- `onKeydown` returns early on ctrl/meta/alt → **no clipboard, no Ctrl+Z**; no `isComposing` →
  IME/composed input (Greek!) does not work.
- No undo at all in the surface (committed edits go through Monaco; while the surface has focus
  Ctrl+Z does nothing).
- `HtmWriter.FormatDivision` degrades to inline `÷` at nesting level ≥ 4, but `mfrac` always
  stacks; **second trigger**: `MathParser.Output.cs:363-364` `formatEquation` — with
  `FormatEquations` off even a shallow `/` renders inline at rest.
- Resting render is engine CSS HTML, editing render is MathML → **font change + the result
  vanishes while editing**. NOT a splitting problem: the editor already owns the expression as
  text. `ExpressionParser.cs:661-671` fuses expression+result in one `<span class="eq">`, so
  they are not separable client-side anyway.

## Deliberate non-goals

Virtual keyboard (the palette covers it), speech/SSML/read-aloud, locales/RTL, the other
serializers, math-level macros, matrix/`mtable` support (a real grammar extension that tensions
the safety gate; source mode already edits matrices cell-by-cell).

## Accepted risk, stated plainly

This design **keeps a second Calcpad grammar on the client** on purpose — it buys offline
editing, zero round-trip latency and no backend change. The mitigation is the fixed-point gate
plus corpus-measured tests, not optimism: extending the bridge without corpus measurement
silently narrows what the gate admits.

# 2026-10-08 (later still) — Palette buttons: dead controls found and fixed

Task: "make every non-functional button interactive; verify no control is dead."

## Audit method (worth reusing)

1. **Quote-aware tag scan** — 117 `<button>` across `calcpad-web/src` + `calcpad-frontend/src`.
   A naive `[^>]*>` regex gives false positives (`v-if="a > 0"`); parse quotes properly.
   Result: **every button has a bound handler**.
2. **Handler-resolution scan** — every `@click` identifier exists in the file's `<script>`
   (12 apparent misses were all `$emit`, a Vue built-in).
3. **Semantic scan** — the real bugs are handlers that *silently do nothing*. The palette
   routes every button through one dispatch, so that is where to look.

## The dead control

`CalcpadMathMlEditor.vue`'s `applyPalette` ended with `if (action.group === 'Structures') return`.
`vector` (`[ ]`) and `matrix2x2` (`2×2`) are in that group with no id mapping → **clicking them
did literally nothing.**

## Fixes

| # | Defect | Fix |
|---|---|---|
| 1 | `vector` / `matrix2x2` dead | new `insertTable` + `mtable` support in the bridge (`[a; b\|c; d]`) |
| 2 | `cbrt` built `root(x; )` — an open degree the button's own tooltip already promised | new `cbrt` `StructureKind` with degree `3` |
| 3 | Palette `/ ÷ ^ _` inserted a **flat glyph** where typing builds a structure | glyph groups now go through `applyCharacter` |
| 4 | `insertPair`/`insertCall` emitted flat brackets; the parser wraps groups in `mrow` | both now wrap, so a typed line and a reloaded one are the same tree |
| 5 | `mergeable('1','x')` was `true` → typing `2x` built `mo('1x')`, which the parser never produces | rewritten to match the tokenizer exactly |
| 6 | `∠` was a *name character* in the bridge, but `Validator.cs` has no `∠` at all — the engine treats it as an operator in `#complex`, else an **error** | modelled as a binary operator |

Also fixed: `applyCharacter('÷')` now builds a fraction, like `/`.

## The invariant that made this findable

`equalNodes(editorTree, calcpadLineToMathMl(mathMlToCalcpadLine(editorTree)))` — **what the
editor holds must be what re-opening its printed text would produce.** Text round-tripping
alone is NOT enough: the gate only ever compares parser-trees, so it can never see the editor
drifting from its own parser. Two of the defects above (4, 5) were invisible to a text-only
check and only showed up as `mo` vs `mn`+`mi`, and flat vs `mrow` brackets.

Verification harness: press all 84 buttons through the real dispatch, finish the edit the way a
user would (fill open slots, then supply the operand a trailing operator awaits), then assert
the invariant. **27 failures → 0.**

## Verification

`tsc` clean; **158 tests pass** (134 baseline → +24); `vue-tsc` clean; `vite build` clean.

## Gotchas

- Python `open(p,'w')` on Windows rewrites `\n` as `\r\n`. The repo sets `* text=auto eol=lf`,
  so git normalizes it and the diff stays clean, but the working tree goes CRLF. Check with
  `data.count(b'\r\n')` in Python — `grep -c $'\r'` in Git Bash reports every line and misleads.
- A "trailing operator" (`x = 1 +`) is a legitimate mid-edit state, the same as `b/`. Tests that
  assert a finished line must supply the missing operand, not treat it as a defect.
- `mtable > mtr > mtd > mrow` is the shape; an empty `mtd` is an `mrow` with no children, which
  is what makes `hasEmptySlot` hold the line open.

# 2026-10-08 (later still) — Graphical editing of HTML and Markdown

Task: "ensure the live editor can edit HTML or Markdown in a graphical way."

User decisions: **WYSIWYG contenteditable**, **both `#html` and `#markdown`**, **markdown as one
block / HTML per line**.

## New module: `calcpad-frontend/src/markup/`

| File | Role |
|---|---|
| `parse-modes.ts` | `parseModeMap` / `markupBlocks` — mirrors `ParseModeTracker`, one pass, mode + directive flag per line |
| `fragment.ts` | `parseFragment` via a `<template>` (see the DOMParser trap below) |
| `html-to-markdown.ts` | the subset + the converter; returns `null` for anything it cannot spell |
| `check.ts` | the gate: refuses anything outside the subset. Validating *is* sanitizing — the subset has no `script`/`style`/`iframe`/`form` and no handler attributes |
| `rendered.ts` | `stripLineAnchors`, `markupBlockHtml` — recovers author markup from the render |
| `commit.ts` | `hasBalancedTags`, `checkMarkupEditable`, `commitMarkupBlock` |
| `CalcpadRichTextEditor.vue` | the contenteditable surface + toolbar (in `calcpad-web/src/live-display/`) |

## The two modes are edited differently

- **`#html`** — one line at a time, and the markup is **the source line itself**. No rendering
  is involved at all: the engine writes an `#html` line verbatim, so the source *is* the markup.
- **`#markdown`** — the whole region at once, markup taken from the elements the engine rendered,
  written back as Markdown via `htmlToMarkdown`.

## Three traps found (all cost real debugging)

1. **`DOMParser` with `text/html` relocates `<script>` and `<style>` into `<head>`.** A checker
   reading `body` therefore passes a fragment containing a script — and the desktop CSP allows
   inline scripts (`script-src 'self' 'unsafe-inline' 'unsafe-eval' https:`), so that is a live
   hole, not a theoretical one. Use `document.createElement('template')` + `template.content`,
   which parses in place and never executes. **This was the single most important find.**
2. **`splitRenderedLines` returns `el.innerHTML`, so the anchored element itself is lost.** For a
   markdown heading the anchored element *is* the `<h2>`; reading only its contents turns it back
   into a paragraph. Added `splitRenderedBlocks` (`el.outerHTML`) and a `blocks` field on
   `LiveRender`; the pane's `Row` now carries both.
3. **Markdig renders a task list as `<input …> done`** — with a space after the checkbox — so a
   naive conversion wrote `- [x]  done` and changed the block on commit. HTML collapses
   whitespace when rendering, so `blockChildren`'s flush now does `replace(/\s+/g,' ')`.

Also: Markdig tags a task list (`class="contains-task-list"` / `task-list-item`) and a code
fence's language (`class="language-js"`). Those exact classes are accepted; any other class is
refused, because dropping it would be a quiet edit.

## Consolidation, not duplication

`text/comment-formatting.ts` already had a `ParseMode` and a `getParseModeAt`. Rather than add a
second tracker, `ParseMode` + `isEndDirective` + `openerMode` now live in `markup/parse-modes.ts`
and `comment-formatting.ts` re-exports them. Its `getParseModeAt` was also **wrong**: it popped on
*any* `#end`, while the engine only pops on the `#end` matching the current mode (`#end markdown`
inside `#html` is content). Fixed.

## Verification

`tsc` clean; **213 tests** (158 → +55); `vue-tsc` clean; `vite build` clean.

End-to-end against the running engine (`splitRenderedBlocks` + the real converter): open a block,
commit with no edit, re-render, require **identical markup** — headings, paragraphs, pipe tables,
bulleted/numbered lists, blockquotes, rules, links, images, task lists, fenced code, mixed
document: **11/11 pass**. `pipe table` and `mixed document` come back respelled (`|------|` →
`| --- |`) with the rendering unchanged; inherent to HTML→Markdown and only reachable when the
user actually edited the block. A multi-line `<style>` is declined per line — correct, and now
asserted as such rather than treated as a defect.

## Server note (again)

`cmd //c "start /b …"` keeps the shell's stdout open, so a command that starts the server *and*
runs something after it gets SIGTERM'd. Use the Bash tool's `run_in_background` instead — that
server survived 14 minutes of repeated test runs.

# 2026-10-08 (later still) — Palette buttons dead in graphical mode: root cause + new UI

Report: "the function- and element-insertion buttons still fail to respond when clicked."

## Root cause — a template ref inside `v-for`

`CalcpadLiveDisplay.vue` binds `ref="mathEditor"` on the math surface, which sits **inside**
`v-for="(row, i) in rows"`. Vue collects a ref inside `v-for` into an **array**, because it
cannot know only one row is ever being edited. So `mathEditor.value` was `[instance]` — truthy,
and with neither `applyPalette` nor `focus`. Every graphical-mode call site threw:

```
TypeError: mathEditor.value.applyPalette is not a function
TypeError: mathEditor.value?.focus is not a function
```

**Five call sites**, all broken since the surface was introduced: the palette insert, the
graphical-mode toggle focus, and click-to-caret (`seekPoint`). Pre-existing — `git show HEAD`
shows the same nesting. Nothing catches it: `vue-tsc` sees `ref<T>` as `T | null` whatever Vue
assigns, and the failure only appears on a click with graphical mode on.

**Fix**: bind as a function ref (`:ref="setMathEditor"`) and normalise through
`singleTemplateRef` (`calcpad-frontend/src/vue/template-ref.ts`).

## The lesson that mattered

I had "verified" these buttons before by testing `applyPaletteAction` (pure) and the catalog —
never the DOM path. **A pure-function test cannot see a component-wiring bug.** The fix was
found by driving the built app in a real browser (Edge via `playwright-core` + a scratch static
server proxying `/api` to the backend), which printed the actual TypeError. Do that whenever the
complaint is "the button does nothing".

## Regression guard

`tests/template-refs.test.ts`:
- `singleTemplateRef` contract.
- A compiler check that a ref inside `v-for` is marked `ref_for: true` — the premise, taken from
  Vue rather than assumed.
- A **static guard** over every `.vue` in both packages: a plain `ref="x"` inside a `v-for` fails
  the suite. Self-tested against the exact shape that broke.

## Alternative UI: a command menu instead of the button grid

84 buttons is a good reference and a poor control — you scan it, look away from the caret, and
reach for the mouse. Replaced as the **primary** control by `CalcpadCommandMenu.vue`:

- **`Ctrl/Cmd+K`** opens it at the caret (works in source and graphical mode; the math surface
  ignores modifier keys so the event reaches the pane).
- Filter-as-you-type over the same catalog; ↑/↓/Home/End navigate, Enter/Tab insert, Esc close.
- **Opens on recency** (`calcpad.live.recentPalette` in localStorage) — `rankPalette` in
  `src/text/palette-search.ts`, pure and tested.
- Inserts through the **same** `applyPalette`, so the two controls cannot drift.
- The grid survives behind a **"Browse symbols"** toggle for looking things up.

`rankPalette` scoring detail worth keeping: the id's **last segment must equal** the query, not
merely end with it — `endsWith('-sin')` ranked `fn-asin` level with `fn-sin`.

## Verification

`tsc` clean; **231 tests** (219 → +12); `vue-tsc` clean; `vite build` clean.
Browser, both modes, **zero console errors**:
- graphical: `√` → `b = a + sqrt(1)`; `sin` → `sin()`; `a⁄b` → a fraction.
- source: `√` → `b = sqrt(a)sqrt()`; `sin` → `...sin()`.
- menu: `Ctrl+K` opens 12 items; `sin` → `["sin","sinh","asin"]`, `sin` first; Enter inserts;
  reopens on `sin`; Esc closes; Browse reveals all 84 and still inserts; ↑↓ moves.

# 2026-10-08 (verification pass) — re-checking the palette fix against the brief

The brief had four parts: investigate the unresponsiveness, identify the root cause, fix the
insertion, and propose an alternative UI. Re-verified each **in a browser**, not from the types.

## What the deeper verification changed

The earlier pass tested **three** buttons (`√`, `sin`, `a⁄b`). Driving **all 84 in both modes**
was the point of this pass, and it found two real defects in the new UI that the sample had missed.

| Found | Verdict |
|---|---|
| All 84 buttons insert, source **and** graphical | **pass** (84/84 + 84/84, no console errors) |
| Root cause + fix across all five call sites | **pass** |
| `Ctrl+K`, filter, Enter, ↑↓, Esc, recency, Browse — **both modes** | **pass** |
| **Menu stayed open when you clicked the surface** | **defect — fixed** (outside-`mousedown` listener) |
| **Palette's folded groups reset on every editor reopen** | **defect — fixed** (state hoisted to the pane) |

Both defects were mine, introduced with the menu in the previous pass.

## Probe lessons (cost real time)

- The palette's **Operators/Relations/Greek groups open folded**, so 54 of the 84 buttons are
  `display:none`. A click probe must expand them — and must **re-expand after every reopen**,
  because the palette remounts and loses the state (that is the papercut above).
- The **source-mode run commits** every edit via Done, so by the time the graphical run starts the
  document is full of half-built expressions and the Graphical checkbox is **disabled**. Give each
  mode a **fresh page**; resetting in place is not enough.
- The graphical mode has no `.live-editor-field[data-field="line"]` — read the line from the
  `Calcpad: <text>, position` status instead, and click `.mathml-surface` for surface clicks.
  A `.catch(() => {})` around a locator click **silently skipped** the graphical case and made a
  broken fix look like a passing one. Do not swallow click failures in a probe.

## Final state

`tsc` clean; **231 tests**; `vue-tsc` clean; `vite build` clean.
Browser: 84/84 buttons respond in both modes, no console errors; the menu behaves in both modes.
